### 核心结论

> **9 份实测，7 份运营商 NAT 为顺序分配，2 份境外VPN出口 NAT 为不规则分配。无一出现真随机端口。**
>
> 国内两大运营商（电信/移动）的 CGNAT 设备，无论 NAT3 还是 NAT4，端口分配器均采用 **"按目标分区 + 区内顺序推进"** 模式。
>
> 另：9 份样本的 IPv6 均不可用（本机无可用 IPv6 地址，或 IPv6 STUN 响应超时/不可达），IPv6 直连暂不能作为国内环境的依赖路径。

### 4.1 预测策略分层

### 4.2 对 NAT4 的特别处理

NAT4 的端口行为并非不可预测：

```
NAT4 预测关键:
  1. 双方互相通告"我当前对这个目标用的端口簇 + 当前簇的步长模型"
  2. 打洞时，双方对准同一目标簇发包
     (信令服务器帮助协调"请切换到对端所在的簇")
  3. 簇内步长 2-12 的预测精度相当于陕西电信 NAT3 的 1-4
  4. 簇跳变后自动重新学习，不中断整体打洞流程
```

### 4.3 境外VPN出口NAT分析（样本8+9专项）

两份VPN样本（美国VPN出口香港、香港VPN出口洛杉矶）首次验证了境外VPN场景下的NAT行为：

**实测结论：**

1. **VPN出口NAT可复现**：两份样本同为Cloudflare AS13335，无论出口在香港还是洛杉矶，NAT行为高度一致——端口受限锥形(NAT3) + 不规则端口分配
2. **步长完全不可预测**：步长分布1-812，小步(≤15)仅占2-3次，大步(101-500)占主导，无任何顺序规律可循
3. **STUN局限性**：VPN隧道隐藏了内层运营商NAT，STUN仅能表征VPN出口NAT行为
4. **RTT稳定在350ms级别**：两份样本RTT均值355-368ms，反映了"广东→Cloudflare边缘节点"的VPN隧道延迟

**为什么VPN出口NAT看起来不规则？**

一个合理的推断：**共享端口池 + 多用户并发**。

```
运营商CGNAT (顺序分配):              共享VPN出口 (多人共用):
                                    
用户A: [端口段 30000-31000]          用户A STUN看到的端口:
  STUN1 → 30001                      28126
  STUN2 → 30003 (+2)                 28086  ← 中间被用户B占了28500
  STUN3 → 30005 (+2)                 27333  ← 被用户C/D占了27600-27900
  STUN4 → 30007 (+2)                 ...
  → 步长规律，可预测                   → 步长乱，不可预测
```

- 运营商CGNAT为每个用户分配独立端口段，段内顺序分配 → **观察有序**
- 共享VPN出口所有用户共用一个端口池，多人并发连接交错分配 → **观察被打乱**
- 端口跨度大(~2000-2500)也印证了共享池的特征——池越大，并发用户越多
- 自建VPN节点（独享端口池）可能表现出顺序分配，待验证

**对穿透策略的指导：**

```
VPN出口NAT穿透策略:
  - 步长预测不可用 → 直接进入兜底策略
  - 扩散穿透窗口: ±3000 (全量撒网)
  - ICMP反推: 关键依赖，用于排除无效端口缩窄搜索范围
  - 发包预算: 47包全部用于VPN出口层
  - 若VPN出口穿透失败 → 回退 TCP/WSS 443 伪装
  
  注意: VPN出口NAT为端口受限锥形(NAT3)，映射一致性好，
        只要端口命中就能建立P2P通道，问题在于"如何命中"
```

**待验证：**
- 非Cloudflare VPN出口（如WireGuard、OpenVPN自建节点）的NAT行为
- VPN出口NAT的ICMP反推排除效率
- 不同VPN协议（UDP/TCP/HTTPS伪装）对穿透的影响
