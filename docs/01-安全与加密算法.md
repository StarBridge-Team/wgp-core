# 一、安全与加密算法

> **修订记录（2026-09-10，对齐 00 架构总览 v1.0）**：
> - 数据面加密移交 QUIC-TLS / TLS-PSK（D3 方案 a），§1.3 的 AES-GCM 帧格式**仅用于 ICMP 逃生通道**
> - §1.4 密钥轮换移交传输层原生能力（QUIC Key Update / TLS KeyUpdate），内核只交付初始会话密钥
> - 后量子密码改为**可选留 API**：KeyAgreement trait + 承诺字段类型标签（见 14 §4），ML-KEM Hybrid 随 rustls 生态随时可开

## 1.1 概述

本项目采用端到端加密（E2EE）架构，所有P2P直连通道的业务数据均经过加密传输。信令服务器仅协助密钥交换与连接协调，被动窃听下**无法解密业务流量**。

> ⚠️ **威胁模型说明**：ECDH 公钥经信令服务器中转，"无法解密"仅在服务器诚实转发时成立；恶意/被攻破的信令服务器可替换公钥实施主动 MITM。缓解方案：**L1 阶段落地承诺-揭示（Commit-then-Reveal）机制（见 §1.2.2）**——服务器在不知私钥的情况下无法替换公钥而不被发现（SHA-256 第二原像抗性保证）。PAKE 为 L3 备选（不采用的原因见 §1.5）。

## 1.2 ECDH 密钥交换算法

### 1.2.1 算法选型

| 参数 | 选择 | 说明 |
|------|------|------|
| 曲线 | **Curve25519 (X25519)** | 比 NIST P-256 更快、更安全，无常数时间攻击风险 |
| 实现 | `x25519-dalek` (Rust) | 经审计的高性能实现，支持 `#![no_std]` |
| 密钥长度 | 256-bit 私钥 / 255-bit 公钥 | 提供约 128-bit 安全强度 |
| 会话密钥派生 | HKDF-SHA256 | 将原始共享密钥扩展为 AES-256 密钥 |

### 1.2.2 密钥交换流程（承诺-揭示，Commit-then-Reveal）

> **设计动机**：信令服务器可替换 ECDH 公钥实施 MITM。承诺-揭示机制使服务器在不知私钥的情况下无法替换公钥而不被发现——服务器必须**先承诺、后揭示**，替换公钥需要找到 SHA-256 第二原像（计算上不可行）。

```
Peer A (Alice)                    信令服务器                    Peer B (Bob)
     |                                 |                            |
     |-- 1. 连接信令通道 --------------->|                            |
     |                                 |<-- 2. 通知 Bob 加入 --------|
     |                                 |                            |
     | 3. 生成临时密钥对 (PrivA, PubA)                               |
     | 4. 生成随机数 nonce_A (32B)                                    |
     | 5. 计算承诺 commit_A = SHA256(PubA || nonce_A)               |
     |                                 |                            |
     |-- 6. 发送承诺 commit_A --------->|                            |
     |                                 |-- 7. 转发 commit_A -------->|
     |                                 |                            |
     |                                 |                            | 8. 生成临时密钥对 (PrivB, PubB)
     |                                 |                            | 9. 生成随机数 nonce_B (32B)
     |                                 |                            |10. 计算承诺 commit_B = SHA256(PubB || nonce_B)
     |                                 |                            |
     |                                 |<-- 11. 发送承诺 commit_B ---|
     |<-- 12. 转发 commit_B -----------|                            |
     |                                 |                            |
     |                                 |  ★ 承诺阶段完成，双方均已锁定公钥 ★        |
     |                                 |                            |
     |-- 13. 揭示 (PubA, nonce_A) ----->|                            |
     |                                 |-- 14. 转发揭示 ----------->|
     |                                 |                            |15. 验证 SHA256(PubA || nonce_A) == commit_A ?
     |                                 |                            |    不匹配 → 立即断连 + 安全告警（MITM 检测）
     |                                 |                            |
     |                                 |<-- 16. 揭示 (PubB, nonce_B)|
     |<-- 17. 转发揭示 ---------------|                            |
     |                                 |                            |
     |18. 验证 SHA256(PubB || nonce_B) == commit_B ?               |
     |    不匹配 → 立即断连 + 安全告警（MITM 检测）                      |
     |                                 |                            |
     |19. 计算 shared = X25519(PrivA, PubB)                        |
     |20. 派生 session_key = HKDF(shared, salt, info)              |
     |                                 |                            |
     |                                 |                            |21. 计算 shared = X25519(PrivB, PubA)
     |                                 |                            |22. 派生 session_key = HKDF(shared, salt, info)

★ 安全保证: 信令服务器在步骤 6-12 已收到双方承诺。若服务器想替换公钥，
   必须在步骤 13 前找到满足 SHA256(PubA' || nonce_A') == commit_A 的碰撞
   ——SHA-256 第二原像抗性使这不可行。服务器唯一能做的攻击是拒绝转发（可用性攻击），
   而非篡改（完整性攻击）。
```

**承诺超时与回退：**

| 条件 | 处理 |
|------|------|
| commit_B 未在 3s 内收到 | 超时断连，不降级为无承诺模式（L1 硬约束） |
| 揭示阶段公钥验证失败 | 立即断连 + 安全告警，记录对端 PeerId 到本地黑名单（24h） |
| 双方承诺相同（碰撞攻击） | 极低概率（2⁻²⁵⁶），检测到则双方重新生成 nonce 重试（最多 1 次） |

### 1.2.3 HKDF 密钥派生细节

```text
输入:
  - ikm (输入密钥材料) = X25519 共享密钥 (32 bytes)
  - salt = SHA256("zheyuemen/v1/ecdh-salt") (32 bytes，固定但公开)
  - info = SHA256(concat(PubA, PubB, nonce_A, nonce_B, ServerTime, "zheyuemen/v1/ecdh")) (防重放纵深；nonce_A/B 绑定承诺阶段随机数，确保密钥与承诺-揭示过程绑定；密钥唯一性由每次全新临时 ECDH 密钥对保证，不依赖 ServerTime)

输出 (标准 HKDF 两阶段流程):
  - prk = HKDF-extract(salt, ikm)                           // 提取阶段
  - okm = HKDF-expand(prk, info, 48)                         // 展开阶段: 32B KEY + 2×8B NONCE_PREFIX（方向隔离）
  - AES_256_GCM_KEY = okm[0..32]                             // 前 32 bytes
  - NONCE_PREFIX_AB = okm[32..40]                            // 方向前缀 AB（Counter 占 4B, Nonce 合计 12B）
  - NONCE_PREFIX_BA = okm[40..48]                            // 方向前缀 BA
```

### 1.2.4 边缘条件与防护

| 场景 | 处理策略 |
|------|---------|
| 公钥长度异常 | 验证 `len(pub) == 32`，不合法则拒绝连接并告警 |
| 低熵共享密钥（全零） | X25519 规范要求 clamp 私钥，依赖 clamping 抵御小群攻击；检查共享密钥是否为零，若为零立即终止连接并记录安全事件（不自动重协商，避免死循环） |
| 重放攻击 | HKDF info 参数包含双方公钥 + ServerTime（信令服务器下发的时间戳），确保每次协商派生密钥唯一 |
| 中间人攻击（MITM） | 承诺-揭示机制（§1.2.2），信令服务器无法替换公钥而不被发现（SHA-256 第二原像抗性）；信令通道 TLS 1.3 提供链路层加密 |
| 密钥协商超时 | 默认 5 秒；高延迟链路按 max(5s, 3×RTT) 放宽（RTT 分级见 04 §4.2），超时未完成则断开并上报"密钥协商失败" |

> **ServerTime 信任模型**：ServerTime 仅作 HKDF 熵源（防重放纵深防御），非安全关键依赖——每次协商均生成全新临时 ECDH 密钥对，共享密钥本身已唯一。客户端须拒绝与本地网络时间锚点偏差 >60s 的 ServerTime（对齐 05 §5.5.2 的 60s 重放窗口），防止信令时间被篡改导致密钥复用。若服务器向双方下发不一致的 ServerTime，双方派生密钥不同导致握手失败——该分支按可用性攻击处理：告警并更换信令通道重试。

## 1.3 AES-256-GCM 数据加密算法

> **适用范围修订（2026-09-10）**：本节帧格式仅用于 **ICMP 逃生通道**（无 TLS 可套的最后一搏链路）。QUIC/TCP 主链路的加密由 TLS-PSK 承担，不用本节格式。

### 1.3.1 算法选型

| 参数 | 选择 | 说明 |
|------|------|------|
| 加密算法 | **AES-256-GCM** | 256-bit 密钥，GCM 模式同时提供加密与 MAC |
| 实现 | `aes-gcm` (RustCrypto) | 纯 Rust 实现，支持硬件 AES-NI 加速 |
| 密钥长度 | 32 bytes (256-bit) | 由 ECDH + HKDF 派生 |
| IV/Nonce 长度 | **12 bytes (96-bit)** | GCM 推荐长度，效率与安全平衡 |
| Tag 长度 | **16 bytes (128-bit)** | 完整认证标签，最强完整性保证 |
| 附加认证数据 (AAD) | 数据包长度字段 + 协议版本号 | 防止长度oracle攻击 |

### 1.3.2 加密数据包格式

```
+------------------+------------------+------------------+------------------+------------------+
|   Packet Length  |  Nonce (12 B)    | Ciphertext (可变) |    GCM Tag      |    Padding      |
|   (2 bytes LE)   |                  |                  |   (16 bytes)    |   (可选, 0-15B) |
+------------------+------------------+------------------+------------------+------------------+
       |                   |                    |                   |              |
       |                   |                    |                   |              +-- 填充到 16 字节边界（抗流量分析）
       |                   |                    |                   +-- 完整性校验
       |                   |                    +-- 加密后的业务数据
       |                   +-- Nonce 构成: NONCE_PREFIX(8B) + Counter(4B)
       +-- 明文传输，用于接收端预分配缓冲区（GCM 解密需要）
```

### 1.3.3 Nonce 管理策略

GCM 在固定密钥下使用相同 Nonce 加密两个不同消息是灾难性的（可恢复密钥）。

```text
Nonce 结构:
  [0..7]  = NONCE_PREFIX (HKDF 派生, 8 bytes, 每 session 固定)
  [8..11] = Counter (4 bytes, big-endian, 严格递增)

Counter 管理（方向隔离，防 Nonce 重用——定稿：方向派生前缀方案）:
  - HKDF 一次展开派生两个方向前缀: NONCE_PREFIX_AB / NONCE_PREFIX_BA（见 1.2.3）
  - 发起方（Alice）发送用 PREFIX_AB、接收用 PREFIX_BA；加入方（Bob）相反
  - 双方 Counter 均从 0 开始，每次加密后 +1，各自独立维护发送/接收 Counter
  - 任一方向 Counter 接近 u32::MAX 时: 触发密钥轮换（重新 ECDH 协商）
  - 两个方向使用不同 NONCE_PREFIX，Nonce 永不重叠（无需 Counter 偏移魔数）
  - 双向同步: 任一方 Counter 达到 u32::MAX × 0.9 时，主动通过信令通道发送 KeyRotationHint 通知对端提前发起轮换，防止一侧先耗尽 Nonce 空间而对端未感知

接收侧重放保护（数据面，与信令面 1024 位图对齐，见 05 §5.5.2）:
  - 接收方按方向维护滑动窗口位图（1024 位），仅接受 Counter 在窗口内且未置位的包
  - 重复 Counter、窗口外 Counter、GCM 校验失败的包一律静默丢弃，不进入转发路径
  - 密钥轮换 30s 双密钥窗口内，旧密钥包同样须过重放窗口
```

### 1.3.4 加密/解密性能要求

| 数据包大小 | 加密耗时目标 | 解密耗时目标 |
|-----------|------------|------------|
| 64 bytes  | < 1 μs     | < 1 μs     |
| 256 bytes | < 2 μs     | < 2 μs     |
| 1460 bytes (MTU) | < 5 μs | < 5 μs   |

> 使用 AES-NI 指令集的现代 CPU 上可达 >1 GB/s 吞吐量。

## 1.4 密钥轮换机制

> **修订（2026-09-10）**：本节轮换流程仅适用于 ICMP 逃生通道的 AES-GCM 密钥。主链路轮换移交 QUIC Key Update（RFC 9001）/ TLS 1.3 KeyUpdate；内核只交付初始会话密钥（14 §10 条款 3、5）。

### 1.4.1 触发条件

| 条件 | 阈值 | 动作 |
|------|------|------|
| 加密数据量 | > 50 GB | 触发密钥轮换 |
| Nonce Counter | 接近 u32::MAX | 触发密钥轮换 |
| 连接时长 | > 24 小时 | 触发密钥轮换 |
| 安全告警 | 任何可疑行为 | 立即轮换 |

> 注：连接缓存（05 §5.5.3 C5）复用的会话密钥仅用于快速重连首包，重连成功后立即触发轮换——缓存不削弱前向保密。

### 1.4.2 轮换流程

1. 任一方发送 `KeyRotationRequest` 信令包
2. 接收方回复 `KeyRotationAccept`，附带新生成的临时公钥
3. 双方在现有加密通道上完成新的 ECDH 协商
4. 新密钥生效前发送 `KeyRotationCommit`
5. 旧密钥保留 30 秒窗口处理正在传输的数据包
6. 30 秒窗口结束后，旧密钥内存必须调用 `zeroize()` 强制清零（使用 zeroize crate），禁止编译器优化
7. 旧密钥相关的 NONCE_PREFIX、Counter 同步擦除
8. 30s 双密钥窗口内：旧密钥**仅解密不加密**，新包一律使用新密钥
9. 密钥材料全生命周期擦除清单（连接断开与轮换完成时均须 zeroize）：X25519 临时私钥、共享密钥、HKDF 中间态（prk/okm）、会话密钥、NONCE_PREFIX、Counter
10. 轮换频率上限：每分钟 ≤1 次，防止伪造"安全告警"触发轮换洪泛（与 §1.2.4 "不自动重协商"策略一致）

## 1.5 为什么不用邀请码 PAKE

邀请码由信令服务器生成并可见（05 §5.2.6），且 8 位 Base36 熵约 41 bit，恶意服务器可离线爆破——SPAKE2 等 PAKE 无法防"知道口令的中转方"。PAKE 仅在"客户端自生成邀请码 + 服务器仅存散列"改造后再评估（L3 备选）。
