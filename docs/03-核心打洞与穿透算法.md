# 三、核心打洞与穿透算法

## 3.1 概述

NAT 打洞是本项目的核心挑战。所有算法围绕 NAT4（对称 NAT）vs NAT4（对称 NAT）这一最难场景进行专门优化。NAT1（Full Cone）、NAT2（Restricted Cone）、NAT3（Port Restricted Cone）因其端口映射行为更宽松，可受益于同一套算法。

**目标成功率**：

| NAT 类型 | 优先级 |
| -------- | ------ |
| Full Cone (NAT1) | 间接受益 |
| Restricted Cone (NAT2) | 间接受益 |
| Port Restricted Cone (NAT3) | 间接受益 |
| Symmetric NAT (NAT4) | **重心** |
| NAT4 + 防火墙 | 建议用户更换网络 |
| 大内网多层 NAT | 尽快报错 |

***

## 3.2 纯 TCP 信令低延迟传输算法

### 3.2.1 概述

信令通道是打洞的大脑，每次信令往返都会直接延迟打洞时机。本算法确保信令在 45-50ms 内完成（国内同运营商场景）。

### 3.2.2 关键优化

| 优化项                     | 技术                          | 效果                        |
| ----------------------- | --------------------------- | ------------------------- |
| **TCP Fast Open (TFO)** | 在 SYN 包中携带首次请求数据            | 节省 1 个 RTT（\~15-30ms）     |
| **信令包压缩**               | 使用定长二进制编码（非 JSON/Protobuf）  | 包体 ≤ 64 bytes，减少 TCP 分段次数 |
| **连接预热**                | 连接建立后立即发送 dummy ping 预分配缓冲区 | 避免后续信令的慢启动                |
| **零分配解析**               | 信令包解析使用 `nom` 或手写解析器，无堆分配   | 解析延迟 < 5 μs               |
| **全双工信令通道**             | 接收和发送使用独立线程，不互锁             | 避免 HOL 阻塞                 |

### 3.2.3 信令包格式

信令包格式详见 [08-折跃门协议技术规范.md](./08-折跃门协议技术规范.md) §5.1，核心字段如下：

```text
信令包通用头部 (16 bytes):
  +----------+----------+----------+----------+
  | Magic    | Version  | MsgType  | Seq      |
  | (2B)     | (1B)     | (1B)     | (4B)     |
  +----------+----------+----------+----------+
  | SessionId           | PayloadLen          |
  | (4B)                | (4B)                |
  +----------+----------+----------+----------+
  | Payload (变长, ≤ 4096 bytes)              |
  +-------------------------------------------+
```

- **Magic**: `0x4D43` ("MC")，用于快速过滤非法包（v1.1 起由 session_key 派生，每会话不同，见 08 §7.4）
- **Version**: 协议版本号 (当前 `0x01`)
- **MsgType**: 信令消息类型（见下方与本算法相关的类型码）
- **Seq**: 序列号 (4B)，用于去重和重传
- **SessionId**: 会话标识 (4B)
- **PayloadLen**: Payload 长度 (4B，上限 4096 bytes)

**本算法涉及的信令类型码**（完整码表见 08 §5.1）：

| Type | 名称 | 说明 | 方向 |
|------|------|------|------|
| 0x01 | HandshakeRequest | 握手请求，含 ECDH 公钥 | 双向 |
| 0x02 | HandshakeResponse | 握手响应，含 ECDH 公钥 | 双向 |
| 0x03 | NatTypeReport | 上报 NAT 类型与端口序列 | 双向 |
| 0x04 | PortSequenceReport | 上报端口预测序列 | 双向 |
| 0x05 | PunchPrepare | 打洞准备，下发打洞参数 | 双向 |
| 0x06 | PunchCommand | 打洞命令，含 T_offset 相对偏移 | 双向 |
| 0x07 | PunchResult | 打洞结果上报 | 双向 |
| 0x08 | Heartbeat | 心跳保活，携带步长校准数据 | 双向 |
| 0x0D | WarmupKeepAlive | 预热保活，维持端口映射不触发步长学习 | 双向 |

### 3.2.4 边缘条件

| 场景            | 处理                                                     |
| ------------- | ------------------------------------------------------ |
| 操作系统不支持 TFO   | 检测 `TcpStream::set_tfo()` 返回值，不支持时降级为标准三次握手            |
| 信令通道丢包        | Seq + ACK 机制：1 秒内未 ACK 则重传，最多 3 次（原 3s 过长，压缩窗口）         |
| 信令通道关闭（服务器重启） | 客户端 exponential backoff 重连（200ms, 500ms, 1s, 2s, max 15s）|
| 信令包乱序         | Seq 去重：接收方记录最近 64 个 Seq 号，重复包静默丢弃                      |

## 3.3 基于时间戳的协调发包同步算法

> 本节实现 Instant + 网络锚点、相对时间戳协调、双模定时器、分级精度降级。

### 3.3.1 核心问题

UDP 打洞要求两个 NAT 设备几乎同时收到对方的包。若发包时间错位超过 NAT 状态表保留时间（通常 5-30 秒），打洞失败。

**关键约束（国内场景）**：信令服务器部署在国内，但跨省/跨境路由下延迟仍可达 30-100ms 且抖动大。**信令服务器无法作为精确时钟源**（RTT/2 假设对称延迟在复杂路由下不严格成立，±1ms 精度不可能实现）。必须改用 Instant + 网络锚点 + 相对时间戳方案，且**禁止读取系统时间**（玩家改时间会直接失效，详见 §3.3.2 硬约束）。

### 3.3.2 时间源设计（禁止 SystemTime，仅用 Instant + 网络锚点）

> **硬约束**：**禁止读取系统时间 `SystemTime::now()`**。玩家修改系统时间会导致 `SystemTime` 跳变，时间戳协调完全失效。所有时间获取**必须**使用单调时钟 `Instant::now()`（Rust 中 `Instant` 基于系统单调时钟，不受系统时间调整影响）。

```text
时间源架构（三层，全部基于 Instant）:

Tier 1: 网络时间锚点（启动时建立，周期校准）
  - 客户端启动时查询网络时间源，记录"Instant 此刻对应的网络时间"
  - 建立映射: net_time_anchor = (instant_at_query, net_timestamp)
  - 后续任意时刻: net_time = net_timestamp + (Instant::now() - instant_at_query)
  - 网络时间源优先级（自动查询，不依赖玩家系统时间）:
      a. NTP: ntp.aliyun.com / ntp.tencent.com / cn.pool.ntp.org（国内首选，延迟低）
      b. HTTP 时间头: 淘宝 mtop 接口 https://acs.m.taobao.com/rest/api3.do?api=mtop.common.getTimestamp
         返回 JSON {"data":{"t":"<毫秒时间戳>"}},解析为网络时间（国内服务，可视为北京时间网络查询）
      c. 信令服务器时间头: 信令响应携带 Date 头（兜底）
  - 校准策略: 启动时自动查询 + 每 30 分钟自动重新校准锚点（全程无需用户介入）
  - 精度: ±5-10ms（NTP）/ ±100ms（HTTP 头）

Tier 2: RTT 相对测量（纯 Instant 差值，不依赖任何绝对时间）
  - 所有延迟测量都用 Instant 差值: rtt = t_recv_instant - t_send_instant
  - 单向延迟估算: one_way ≈ RTT/2（假设对称路径）
  - 用于信令 RTT 补偿、Peer 互助时间同步
  - 优势: 玩家改系统时间完全不影响 RTT 测量

Tier 3: Peer 互助时间锚点（兜底）
  - 向已连接 Peer 发送时间探测包（携带 Instant 相对偏移）
  - Peer 回复其 net_time_anchor，本地用 RTT/2 补偿
  - 精度 ±20-50ms（取决于 Peer 间 RTT）

关键原则:
  - 任何代码路径禁止出现 SystemTime::now()
  - 所有"绝对时间"需求通过 net_time_anchor + Instant 差值换算
  - 所有"相对定时"需求直接用 Instant::now() + Duration
  - 玩家改系统时间 → Instant 不受影响 → 协调正常工作
```

### 3.3.3 相对时间戳协议（去绝对时间戳，纯 Instant 协调）

**核心改变**：信令不下发绝对打洞时间戳，改为约定"相对偏移"，双方各自用 `Instant` 计算打洞时刻，完全不读取系统时间。

```text
相对时间戳协议:

1. 信令约定阶段（信令只传相对偏移，不传绝对时间）:
   a. 信令服务器向双方下发: T_offset = 3s（3 秒后开始打洞）
   b. Alice 收到后记录本地 Instant: t_recv_A = Instant::now()
   c. Bob 收到后记录本地 Instant: t_recv_B = Instant::now()
   d. 双方各自计算本地打洞 Instant:
      - T_send_A = t_recv_A + T_offset（Alice 单调时钟）
      - T_send_B = t_recv_B + T_offset（Bob 单调时钟）

2. 时钟偏差补偿阶段（基于网络锚点，非 SystemTime）:
   e. Alice 和 Bob 通过 Tier 1 网络锚点获取各自 net_offset_A, net_offset_B
      （net_offset = net_time_anchor 相对 UTC 的偏差）
   f. 双方通过信令交换 net_offset，计算相对偏差 delta = net_offset_A - net_offset_B
   g. 调整: 若 |delta| > 阈值，Bob 调整本地打洞时刻 T_send_B += delta
   h. 注意: delta 的计算用 net_time_anchor（Instant 派生），不用 SystemTime

3. 同步发包阶段:
   i. Alice 在 T_send_A 时刻（Instant 比较）调用 sendto()
   j. Bob 在 T_send_B 时刻（Instant 比较）调用 sendto()
   k. 定时实现: loop { if Instant::now() >= T_send { sendto(); break } }

优势:
  - 信令只传"T_offset = 3s"，不依赖信令时钟精度
  - 打洞时刻基于 Instant 计算，不受系统时间调整影响
  - 玩家改系统时间 → Instant 不变 → 协调正常
  - 时钟偏差通过网络锚点独立获取，不依赖信令 RTT
```

### 3.3.4 精度分级与降级策略

**按本地时钟偏差分级，动态调整打洞窗口和探测策略**：

| 时钟偏差 | 精度等级 | T_punch 缓冲 | 探测策略 |
|---------|---------|-------------|---------|
| < 10ms（NTP 同步良好） | ±1ms 高精度 | 150ms | 标准三波 21+15+11 |
| 10-30ms（NTP 正常） | ±10ms 中精度 | 300ms | 三波 21+15+11（必要时补波 15 包，总 62 包，受会话总预算 ≤500 包/10 分钟约束） |
| 30-100ms（NTP 降级） | ±50ms 低精度 | 500ms | 连续探测流（每 100ms 发 10 包，持续 2s） |
| > 100ms（无 NTP） | 放弃精确协调 | — | 持续发包模式（每 200ms 发 15 包，持续 5s） |

```text
持续发包模式（低精度兜底）:

  适用: 时钟偏差 > 100ms，无法精确协调
  策略: 放弃"同时发包"，改为"持续发包等对方 NAT 表项建立"

  Alice: 每 200ms 发 15 包 → 持续 5 秒（共 375 包，超 80 pkt/s 限制需降低发送速率）
  Bob:   每 200ms 发 15 包 → 持续 5 秒

  原理: 只要一方的包先到达对方 NAT 建立映射，对方后续包就能进入
        不依赖精确时间协调，代价是包数多、耗时长

  注意: 此模式带宽消耗大，仅在低精度兜底时使用
        NAT 类型为 NAT4 时可放宽到 120 pkt/s
```

### 3.3.5 双模定时器（高精度 + 相对定时器）

打洞窗口期极短（NAT 状态表 5-30s，苛刻环境 < 5s），定时器精度直接决定打洞成败。本系统采用**双模定时器架构**：高精度定时器为主，相对定时器为辅，高精度失效时**无感切换**到相对定时器。

```rust
// Rust 双模定时实现
use std::time::{Instant, Duration};

/// 定时器模式
enum TimerMode {
    /// 高精度模式：忙等待 + sleep，精度 < 1ms
    HighPrecision,
    /// 相对模式：纯 sleep + 单调时钟补偿，精度 ~10ms，CPU 占用极低
    Relative,
}

struct DualModeTimer {
    target: Instant,
    mode: TimerMode,
    /// 高精度模式连续失败次数，超过阈值自动切换到相对模式
    hp_fail_count: u32,
    /// 相对模式运行时长，定期尝试回切高精度
    relative_duration: Duration,
}

impl DualModeTimer {
    fn new(delay: Duration) -> Self {
        Self {
            target: Instant::now() + delay,
            mode: TimerMode::HighPrecision,
            hp_fail_count: 0,
            relative_duration: Duration::ZERO,
        }
    }

    /// 等待到目标时刻，自动选择模式
    fn wait_for_target(&mut self) {
        match self.mode {
            TimerMode::HighPrecision => self.wait_high_precision(),
            TimerMode::Relative => self.wait_relative(),
        }
    }

    /// 高精度等待：精度 < 1ms
    fn wait_high_precision(&mut self) {
        let start = Instant::now();
        // 第一阶段: 正常 sleep (剩余 > 3ms)
        while Instant::now() < self.target - Duration::from_millis(3) {
            std::thread::sleep(Duration::from_millis(1));
        }
        // 第二阶段: 忙等待 (剩余 < 3ms)
        while Instant::now() < self.target {
            std::hint::spin_loop();
        }
        // 检测 CPU 占用：如果忙等耗时异常高，累计失败次数
        let elapsed = start.elapsed();
        if elapsed > Duration::from_millis(50) && elapsed.as_millis() > self.target.duration_since(start).as_millis() * 2 {
            self.hp_fail_count += 1;
        }
        // 连续 3 次高精度异常 → 无感切换到相对模式
        if self.hp_fail_count >= 3 {
            self.mode = TimerMode::Relative;
            self.hp_fail_count = 0;
        }
    }

    /// 相对等待：精度 ~10ms，零忙等，CPU 友好
    fn wait_relative(&mut self) {
        let start = Instant::now();
        if self.target > start {
            let remaining = self.target - start;
            // 粗粒度 sleep，留 10ms 余量
            if remaining > Duration::from_millis(10) {
                std::thread::sleep(remaining - Duration::from_millis(10));
            }
            // 最后 10ms 用短 sleep 填补（非忙等，保护 CPU）
            while Instant::now() < self.target {
                std::thread::sleep(Duration::from_millis(2));
            }
        }
        self.relative_duration += start.elapsed();
        // 相对模式运行超过 30s → 尝试回切高精度（可能系统已恢复）
        if self.relative_duration > Duration::from_secs(30) {
            self.mode = TimerMode::HighPrecision;
            self.relative_duration = Duration::ZERO;
        }
    }
}
```

**无感切换触发条件**：

| 触发条件 | 切换方向 | 说明 |
|---------|---------|------|
| 高精度忙等 CPU 占用 > 80% 持续 3 次 | 高精度 → 相对 | 系统负载过高，忙等加剧卡顿 |
| 检测到移动设备省电模式 | 高精度 → 相对 | 节能模式下 CPU 频率降低，忙等精度退化 |
| 操作系统不支持高精度定时（旧 Windows） | 高精度 → 相对 | 启动时探测，直接使用相对模式 |
| 相对模式运行 > 30s | 相对 → 高精度（尝试回切） | 定期探测系统是否恢复 |
| 打洞关键时刻（T_send 前 50ms） | 临时强制高精度 | 关键发包不妥协精度 |

### 3.3.6 边缘条件

| 场景 | 处理 |
|------|------|
| 客户端时钟明显异常（NTP offset > 5s） | 客户端告警，强制重新 NTP 同步；同步失败则用持续发包模式 |
| NTP 服务器不可达 | 降级到信令 RTT 补偿（Tier 2）或 Peer 互助时间同步（Tier 3） |
| 双方 NTP offset 偏差大（> 100ms） | 放弃精确协调，进入持续发包模式（§3.3.4 第 4 档） |
| RTT 波动（网络抖动） | NTP 多次查询取中位数；信令 RTT 测量 5 次取中位数 |
| 单方未能在 T_punch 前确认 | 本地定时器超时后自动开始发包，不等对方确认（避免无限等待） |
| 忙碌等待导致 CPU 100% | 双模定时器自动切换到相对模式，零忙等 |
| 相对模式精度不足导致发包错位 | 关键时刻（T_send 前 50ms）临时强制高精度，牺牲短暂 CPU 换精度 |

## 3.4 运营商差异化端口预测算法

> 本节实现单次 STUN 探测学习步长。

### 3.4.1 核心思想

对称 NAT（NAT4）为每个目标 `(IP, Port)` 分配不同的公网端口，这是 P2P 穿透的核心障碍。传统做法是盲猜，成功率极低（< 5%）。本算法通过**步长学习**将盲猜转化为测量+预测。

**理论基础**：运营商 NAT 设备（华为/中兴/爱立信等）普遍使用顺序端口分配器，极少使用真随机。实测覆盖电信 NAT3/NAT4（五地市）、移动 NAT3/NAT4（两地市），**无一出现真随机端口分配**。

**实测端口行为（2026-06-26 至 2026-07-17，七报告，六地市两运营商）**：

| 样本 | NAT | 端口行为 | 区内步长 | 跨度 |
|------|-----|---------|---------|------|
| 湖南长沙 电信 | NAT3 | 单簇顺序 | 1-320 | ~4032 |
| 陕西西安 电信 | NAT3 | 单簇顺序，**极致小步** | **1-4 (94%)** | **仅 93** |
| **四川马尔康** 电信 | NAT3 | 单簇顺序 | 1-90 (70%≤15) | ~372 |
| 广东河源 电信 | **NAT4** | **双簇+区内顺序** | **2-12** | 每簇~178 |
| 广东广州 移动 | **NAT4** | **多簇+子跳变+区内顺序** | **3-14** | 每簇~150 |
| 广东惠州 电信（非宽带） | NAT3 | 单簇顺序，**双向波动** | **-36~+61** | ~120 |
| 广东龙川 移动（宽带） | NAT3 | 单簇顺序 | **2-13 (80%)** | ~241 |

**关键结论**：
- 电信 CGNAT（NAT3/NAT4）均为 **按目标分区 + 区内顺序分配**。跨省行为统一（AS4134），差异取决于设备批次
- 移动 CGNAT（NAT4 流量/热点）亦为 **多簇 + 区内顺序分配**，簇间有跳变（+225~+474），簇内步长 3-14
- 电信 NAT4 表现为不同目标 IP 触发不同端口簇；同目标连续请求端口稳定（10/10 全命中）
- 移动家宽（龙川，2026-07-17）已补测：**单簇顺序、步长 2-13**；移动流量侧（广州）已确认**多簇 + 区内顺序分配**

> **核心突破**：不再假设"端口完全随机"，而是**先做 3 次 STUN 学习步长模式，然后通过信令互通步长信息，集中探测预测窗口**。

### 3.4.2 步长学习算法

```rust
/// 学习阶段：向不同 STUN 目标发 3 次请求，建立步长模型
struct PortStepModel {
    last_port: u16,           // 最后一次 STUN 得到的端口
    mean_delta: f64,          // 平均步长
    delta_range: (i32, i32),  // 步长范围 (min, max)
    trend: Trend,             // 趋势
    confidence: f64,          // 置信度 (0.0 - 1.0)
}

enum Trend {
    Increasing,    // 单调递增
    Decreasing,    // 单调递减（回退型）
    Oscillating,   // 震荡型（有正有负）
}

impl PortStepModel {
    fn learn(probes: &[(u16, u16)]) -> Self {
        // probes: [(local_port, public_port), ...]
        assert!(probes.len() >= 3, "至少需要 3 次 STUN 探测");
        
        let deltas: Vec<i32> = probes.windows(2)
            .map(|w| w[1].1 as i32 - w[0].1 as i32)
            .collect();
        
        let mean_delta = deltas.iter().sum::<i32>() as f64 / deltas.len() as f64;
        let min_delta = *deltas.iter().min().unwrap();
        let max_delta = *deltas.iter().max().unwrap();
        
        let trend = if min_delta > 0 && max_delta > 0 {
            Trend::Increasing
        } else if max_delta < 0 && min_delta < 0 {
            Trend::Decreasing
        } else {
            Trend::Oscillating
        };
        
        // 置信度：步长越一致，置信度越高
        let variance: f64 = deltas.iter()
            .map(|&d| (d as f64 - mean_delta).powi(2))
            .sum::<f64>() / deltas.len() as f64;
        let confidence = 1.0 / (1.0 + variance / 100.0);
        
        PortStepModel {
            last_port: probes.last().unwrap().1,
            mean_delta,
            delta_range: (min_delta, max_delta),
            trend,
            confidence,
        }
    }
    
    /// 预测对方下次请求我们的真实地址时，NAT 会分配的端口
    fn predict_peer_port(&self, peer_model: &PortStepModel, round: u8) -> PredictWindow {
        // 对方刚做完 STUN，当前端口 = peer_model.last_port
        // 对方下一步要请求我们的地址，NAT 会分配新端口
        // 预测 = peer_last_port + 对方步长 * 安全系数
        
        let base = peer_model.last_port;
        let delta = peer_model.mean_delta;
        
        // 安全系数：步长波动越大，窗口越宽
        let span = peer_model.delta_range.1 - peer_model.delta_range.0;
        let safety = 1.0 + span as f64 / 1000.0;  // ±3000时安全系数=4
        
        let pred_port = (base as f64 + delta * safety) as u16;
        
        PredictWindow {
            center: pred_port,
            half_width: (50.0 * safety) as u16,  // 预测窗口宽度
            confidence: peer_model.confidence,
        }
    }
}
```

### 3.4.3 信令互通步长信息

```text
Alice 做完 3 次 STUN 学习:
  └→ 得到: (last_port=3105, mean_delta=+55, trend=Increasing, confidence=0.92)
  └→ 通过信令服务器发给 Bob:
       含: last_port + mean_delta + delta_range + trend + confidence

Bob 同理发给 Alice

双方知道了:
  ├── 对方的步长模型
  ├── 对方的端口预测窗口大小
  └── 对方模型的置信度

低置信度处理:
  └→ confidence < 0.5 → 退化为宽泛探测（±3000 大撒网）
```

### 3.4.4 运营商差异与自适应性

基于实测（电信 NAT3 三省 + 电信 NAT4 + 移动 NAT4），端口分配行为已知为**按目标分区 + 区内顺序分配**。算法设计为自适应的，不硬编码运营商行为：

| 步长特征 | 预测策略 | 窗口宽度 | 置信度 |
|---------|---------|---------|--------|
| 区内小步 (±1~15) | 精准预测 | ±50 | 高 (>0.85) | 陕西电信、广东电信 NAT4、广东移动 |
| 区内中步 (±16~320) | 中等预测 | ±400 | 中 (0.5-0.85) | 湖南电信 |
| 簇间跳变 (+200~500) | 检测跳变、重新建簇 | 当前簇±50 + 新簇大撒网 | 特殊 | 移动热点（频繁跳变建新簇） |
| 簇间大幅跳变 (>2000) | 宽泛预测 | ±3000 | 低 (<0.5) | 电信 NAT4 切换目标 IP 时 |
| 震荡/真随机 | 不预测（退化为三波大撒网） | ±3000 | 极低 | 未在实测中出现，作为兜底保留 |

### 3.4.5 边缘条件

| 场景 | 处理 |
|------|------|
| 历史数据不足（首次打洞，STUN < 3次） | 退化为宽泛探测，±3000 大撒网 |
| 端口循环回绕（65535 → 1024） | 检测 wrapping_sub，标记 confidence=0 |
| ISP 变更 NAT 分配策略 | 窗口持续更新，新数据覆盖旧模型 |
| 步长为负（回退） | 第二波回退自动覆盖，见 §3.5 |
| confidence=0（不可学习） | 启用三波大撒网，同时尝试 TCP 伪装打洞 |

## 3.5 三波探测策略

> 本节实现 21+15+11 完整三波。

### 3.5.1 核心思想

基于步长学习结果，分三波探测，层层递进：

```text
第一波（精准预测）: 学习成功 → 集中探测预测窗口
     ↓ 800ms 无响应
第二波（回退兜底）: 覆盖步长为负/回退/突变的情况
     ↓ 仍无响应
第三波（大撒网保底）: ±3000 范围全覆盖
```

### 3.5.2 探测参数表

```
┌─────────┬──────────┬────────┬─────────┬──────────┬─────────────┐
│ 学习结果  │ 预测窗口  │ 包数    │ 回退包  │ 第三波包  │ 总包数(Max) │
├─────────┼──────────┼────────┼─────────┼──────────┼─────────────┤
│ 高置信度  │ ±50      │ 21     │ 15      │ —        │ 36          │
│ 中置信度  │ ±400     │ 21     │ 15      │ 11       │ 47          │
│ 低置信度  │ ±3000    │ 21     │ 15      │ 11       │ 47          │
│ 无数据    │ ±3000    │ —      │ —       │ 36       │ 36          │
└─────────┴──────────┴────────┴─────────┴──────────┴─────────────┘

每包大小: ~31 bytes (UDP净荷，含 AuthTag 12B) / ~10 bytes + TCP头 (TCP净荷)
（含 IP/UDP 头部开销后约 55 bytes，按 64 bytes 保守估算）
最大带宽: 47 × 64 ≈ 3 KB，一秒内发完 ≈ 24 Kbps
远低于 80 pkt/s DDoS防御上限
（合规：探测仅针对建立自身通信所需的 NAT 映射，速率自限，不针对他人设备）
```

### 3.5.3 三波时序

```text
STUN 学习 (3次, 约 600ms)
     ↓
信令互通步长 (约 1 RTT)
     ↓
第一波: 预测窗口 21 包
     ├─ 800ms 超时
     ├─ 命中 → 打洞成功 ✓
     └─ 未命中 ↓
第二波: 回退窗口 15 包 (向负方向覆盖)
     ├─ 800ms 超时
     ├─ 命中 → 打洞成功 ✓
     └─ 未命中 ↓
第三波: 大撒网 11-36 包 (仅低置信度触发)
     ├─ 800ms 超时
     ├─ 命中 → 打洞成功 ✓
     └─ 未命中 → 失败，触发协议切换或 TCP 伪装

总耗时（最坏情况）:
  学习(600ms) + 信令(1RTT≈50ms) + 探测(3×800ms) ≈ 3.05s
总耗时（最佳情况）:
  学习(600ms) + 信令(1RTT≈50ms) + 第一波击中(0ms) ≈ 650ms
总耗时（高置信度最坏，两波）:
  学习(600ms) + 信令(1RTT≈50ms) + 探测(2×800ms) ≈ 2.25s
```

### 3.5.4 双向通信

只要一方打进去，双向通信即可建立。

> 扩散穿透（多层 NAT 场景）详见 03-2 文档，含 LayerProbe 层数探测与三层扩散设计，失败回退至三波探测。

### 3.5.5 探测包内容最小化

```text
UDP 探测包格式:
  [Magic(2B) | Type(1B) | PeerId(4B) | Nonce(4B) | Timestamp(8B) | AuthTag(12B)]
  总计 31 bytes
  AuthTag = HMAC-SHA256(punch_key, 前 19B) 截断 12B，punch_key 由 ECDH 会话密钥派生
  （防伪造打洞包 / port stealing，校验失败静默丢弃，格式定稿见 08 §5.2）

TCP 探测包格式:
  [SYN 标志 | Magic(2B) | PeerId(4B) | Nonce(4B)]
  总计 10 bytes + TCP 头部
```

### 3.5.6 边缘条件

| 场景 | 处理 |
|------|------|
| 第一波全部命中但被防火墙丢弃 | 不扩大范围，改用 TCP SYN 伪装重发 |
| 第二波步长反向超过预期 | 扩大回退窗口到 -500，最多 20 包 |
| 第三波大撒网仍失败 | 报告探测失败，触发高延迟补偿或协议切换 |
| 双方 confidence 都不足 0.5 | 跳过步长学习，直接三波大撒网 + 多轮重试 |
| 探测包被运营商 QoS 限速 | 降低发送速率到 40 pkt/s，延长超时 |
| 中间 NAT 状态表刷新 | 利用时序压缩窗口（150ms），在 NAT 表过期前完成 |

## 3.6 对称 NAT 与防火墙协同交互算法

### 3.6.1 对称 NAT 识别

在打洞尝试前，先通过 STUN 协议确定双方的 NAT 类型：

```text
NAT 类型判定（RFC 3489 变种 + 自定义扩充）:

1. 发送 STUN Binding Request 到服务器 IP-A:Port-A
   - 收到响应 → 获取映射地址 MappedAddrA
   
2. 发送 STUN Binding Request 到服务器 IP-B:Port-B (不同 IP)
   - 收到响应 → 获取映射地址 MappedAddrB
   
3. 比较 MappedAddrA 和 MappedAddrB:
   - 地址和端口都相同 → Full Cone (不依赖目标)
   - 地址相同、端口不同 → Restricted Cone 或 Port Restricted Cone
   - 地址和端口都不同 → Symmetric NAT ← 需要重点处理
```

### 3.6.2 对称 NAT + 防火墙协同策略

```text
当判定为 Symmetric NAT 且防火墙已识别（详见 3.10 节）时:

策略 A: 端口预测优先
  适用: 运营商端口分配有规律可循
  执行: 3.4 节端口预测 + 3.5 节并行探测

策略 B: 防火墙端口复用
  适用: 防火墙有状态检测且允许已建立连接的回包
  执行:
    1. 向信令服务器 IP:Port 发送 UDP 包 (建立 NAT 映射)
    2. 在防火墙状态表超时前 (通常 30-60s)，迅速向对端预测端口发包
    3. 利用已有映射 "附带" 发往新目标

策略 C: 多路复用单端口
  适用: SO_REUSEPORT 可用
  执行:
    1. 绑定同一本地端口到多个 UDP socket
    2. 每个 socket 向不同目标发送
    3. 期望至少一个 socket 的映射端口落入对方探测范围

策略 D: TCP 打洞
  适用: UDP 完全受阻
  执行:
    1. 使用 TCP 的 TIME_WAIT 状态复用五元组
    2. 见 3.11 节三次握手变种算法
```

### 3.6.3 防火墙与 NAT 协同探测

| 场景                    | 处理                          |
| --------------------- | --------------------------- |
| NAT 类型在打洞过程中变化        | 实时检测映射地址突变，发现变化立即触发类型重判定    |
| 防火墙状态表超时 < 5s         | 极苛刻环境，放弃打洞并提示用户             |
| CGNAT（运营商级 NAT）       | 多层映射增加预测难度，尝试策略 C（多路复用）+ 预测 |
| Symmetric NAT 端口分配真随机 | 标记为"不可穿透"，终止尝试并明确告知用户       |

## 3.7 心跳包的动态频率保活算法

### 3.7.1 目标

维持 NAT 映射不被删除，同时最小化心跳带宽消耗。

### 3.7.2 动态频率调整

```rust
struct HeartbeatController {
    base_interval: Duration,    // NAT 超时时间的 1/4 (初始猜测)
    min_interval: Duration,     // 最小间隔 (500ms, 抢在 NAT 表过期前)
    max_interval: Duration,     // 最大间隔 (15s)
    success_window: VecDeque<bool>, // 滑动窗口 (最近 20 次)
    
    next_interval: Duration,
}

impl HeartbeatController {
    fn new() -> Self {
        Self {
            base_interval: Duration::from_millis(2000), // 假设 NAT 超时 8s, 取 1/4
            min_interval: Duration::from_millis(500),
            max_interval: Duration::from_secs(15),
            success_window: VecDeque::with_capacity(20),
            next_interval: Duration::from_millis(2000),
        }
    }
    
    fn on_result(&mut self, success: bool) {
        self.success_window.push_back(success);
        if self.success_window.len() > 20 {
            self.success_window.pop_front();
        }
        
        let rate = self.success_window.iter()
            .filter(|&&s| s).count() as f64 / self.success_window.len() as f64;
        
        if rate < 0.8 {
            // 响应率不足，加快心跳（步长 500ms）
            self.next_interval = max(
                self.next_interval.saturating_sub(Duration::from_millis(500)),
                self.min_interval
            );
        } else if rate > 0.95 && self.next_interval < self.max_interval {
            // 响应良好，降低频率
            self.next_interval = min(
                self.next_interval + Duration::from_secs(1),
                self.max_interval
            );
        }
    }
}
```

### 3.7.3 心跳与步长学习融合

> 本节实现端口监控、PortShifted 自动调整。

**心跳包不仅是保活工具，更是持续校准端口预测模型的数据源。**

```text
连接建立后，心跳包扩展为携带步长校准信息:

┌─────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│Type=0x02│ Seq (4B) │ Magic(2B)│AuthTag(12B)│当前端口(2B)│ 上轮端口(2B)│
│保活标记  │          │          │            │ cur_port  │ prev_port │
└─────────┴──────────┴──────────┴────────────┴──────────┴──────────┘
  基础: 19 bytes + 扩展: 4 bytes = 23 bytes（AuthTag 见 08 §5.3）

扩展字段说明:
  cur_port: 本次心跳发送时 NAT 分配的公网端口
  prev_port: 上一次心跳时使用的公网端口
  
  → 接收端可根据两个端口差计算步长: delta = cur_port - prev_port
  → 每条心跳都更新一次 PortStepModel
  → 如果发生端口突变（步长 > 统计预期），触发"重新学习"标记
```

**心跳步长学习逻辑：**

```rust
struct HeartbeatStepTracker {
    step_model: PortStepModel,      // 复用心跳数据持续更新
    anomaly_count: u8,              // 连续异常次数
    re_learn_threshold: u8,         // 触发重新学习的阈值
}

impl HeartbeatStepTracker {
    fn on_heartbeat(&mut self, cur_port: u16, prev_port: Option<u16>) {
        if let Some(prev) = prev_port {
            let delta = cur_port as i32 - prev as i32;
            
            // 检测异常：步长超出历史范围 3 倍
            let range = self.step_model.delta_range;
            let expected_max = range.1.abs().max(range.0.abs()) * 3;
            
            if delta.abs() > expected_max {
                self.anomaly_count += 1;
                if self.anomaly_count >= self.re_learn_threshold {
                    // NAT 端口分配策略可能变化，标记需要重新学习
                    self.step_model.confidence = 0.0;
                    // 通知信令层发起新的 STUN 学习轮次
                }
            } else {
                self.anomaly_count = self.anomaly_count.saturating_sub(1);
                // 正常步长，更新模型
                self.step_model.update(delta);
            }
        }
    }
}
```

### 3.7.4 心跳包最小化

```text
基础格式 (19 bytes):
  +----------+----------+----------+----------------+
  | Type=0x02 | Seq (4B) | Magic (2B) | AuthTag (12B) |
  +----------+----------+----------+----------------+

扩展格式 (23 bytes, 携带端口步长校准):
  [基础格式 19B] + [cur_port(2B) | prev_port(2B)]
  （AuthTag = 截断 HMAC-SHA256(hb_key)，v1.1 起替代明文 CRC32，见 08 §5.3）

策略:
  - 默认每 10 次心跳发送一次扩展格式（携带步长数据）
  - 检测到异常后，连续 3 次心跳都发送扩展格式
  - 重新学习完成后恢复默认频率
  - 额外带宽: 4 bytes × (1/10 + 3/异常后) ≈ 可忽略
```

### 3.7.5 边缘条件

| 场景 | 处理 |
|------|------|
| 一次心跳超时不等于 NAT 失效 | 使用滑动窗口累计成功率，容忍少量丢包 |
| 设备休眠/挂起后恢复 | 恢复后立即发送 3 次快速心跳（间隔 100ms），重建映射，同时携带扩展格式用于端口突变检测 |
| NAT 超时时间突变 | 窗口统计自动适配，从失败恢复后频率自动提高 |
| 长时间无数据交互（挂机） | 心跳退回到最大间隔 15s（原 30s 过长），节省电量；每次心跳携带扩展格式监控端口是否漂移 |
| 心跳检测到步长突变 | 连续 3 次异常 → confidence 归零 → 触发 STUN 重新学习 → 通过信令通知对端更新步长模型 |
| 连接稳定期（> 60s 无异常） | 心跳包退化为纯基础格式（19B），节省扩展字节 |

## 3.8 NAT 映射超时自适应学习算法

> **背景**：不同 NAT 设备的映射超时差异巨大（NAT1 cone 可能 5 分钟，NAT4 symmetric 可能 30 秒）。当前 §3.7 心跳为动态间隔（500ms–15s，初始 2s），但未按 NAT 类型差异化。本算法通过在线学习每个 Peer 的真实 NAT 超时，动态调整保活间隔。

### 3.8.1 学习状态机

```rust
struct NatTimeoutLearner {
    // 当前保活间隔（Instant 相对定时，不读 SystemTime）
    current_interval: Duration,
    // 学习状态
    state: LearnState,
    // 该 Peer 的历史观测超时（毫秒，Instant 差值）
    observed_timeouts: Vec<Duration>,
    // 连续无断连时长（Instant 派生）
    stable_duration: Duration,
}

enum LearnState {
    /// 初始保守模式（25s 间隔）
    Conservative,
    /// 试探增长模式（逐步加大间隔）
    Probing,
    /// 稳态模式（找到最优间隔）
    Stable,
    /// 断连恢复模式（间隔砍半回退）
    Recovering,
}
```

### 3.8.2 学习流程

```text
启动: current_interval = 25s（保守值），state = Conservative

阶段 1 - Conservative → Probing（连续 10 分钟无断连）:
  - 进入 Probing 状态
  - current_interval += 5s（试探 30s）
  - 继续观察 10 分钟，若仍无断连 → 继续加 5s
  - 上限: 120s（NAT1 cone 理论上限）

阶段 2 - Probing → Stable（找到断连临界点）:
  - 若某次保活后发生断连（对端无响应）:
    a. 记录 observed_timeout = 当前 current_interval
    b. 回退到上一个成功间隔: current_interval = 上次值 - 5s
    c. state = Stable，记录该 Peer 的最优间隔
    d. 缓存到本地（关联 Peer ID + NAT 类型）

阶段 3 - Stable 维持:
  - 按学习到的最优间隔保活
  - 每 30 分钟做一次试探（间隔 +5s），确认 NAT 超时未变
  - 若试探失败 → 回退并保持 Stable

阶段 4 - 断连恢复（网络变化时）:
  - 检测到断连 → state = Recovering
  - current_interval 砍半回到 25s（保守值）
  - 重新进入 Conservative → Probing 流程
  - 触发条件: 网络切换（WiFi↔4G）、系统休眠恢复
```

### 3.8.3 收益预估

| NAT 类型 | 固定间隔带宽 | 学习后间隔 | 带宽节省 |
|---------|------------|-----------|---------|
| NAT1（cone，5min 超时） | 25s × 23B ≈ 0.92 B/s | 120s × 23B ≈ 0.19 B/s | **79%** |
| NAT2/3（restricted，2min 超时） | 25s × 23B ≈ 0.92 B/s | 60s × 23B ≈ 0.38 B/s | **58%** |
| NAT4（symmetric，30s 超时） | 25s × 23B ≈ 0.92 B/s | 25s × 23B（保持） | 0%（不降级保稳定） |

**关键特性**：纯客户端逻辑，不增加服务器负担，不违反任何硬约束。学习结果缓存到本地，重连同一 Peer 时直接复用。

## 3.9 后台预探测算法（零等待连接）

> **背景**：当前流程是"发起连接 → 才探测 NAT 类型 + NTP 同步 + STUN 探测"，用户感知延迟 3-5s。本算法在客户端启动时后台并行预探测，使用户发起连接时几乎瞬时进入打洞阶段。

### 3.9.1 预探测任务清单

```text
客户端启动 → 后台并行执行（不阻塞 UI）:

任务 1: 网络时间锚点建立（§3.3.2 Tier 1）
  - 查询 NTP 或 HTTP 时间头
  - 建立 net_time_anchor = (Instant, net_timestamp)
  - 耗时: 100-500ms

任务 2: 本地 NAT 类型探测 + 公网地址获取
  - 向 STUN 服务器发送探测包
  - 获取 NAT 类型 + 公网 IP + 公网端口
  - 缓存 5 分钟（过期后后台刷新）
  - 耗时: 200-800ms

任务 3: IPv6 入站可用性探测（§6.3.1 步骤 1.3）
  - STUN IPv6 回显探测
  - 缓存 5 分钟
  - 耗时: 0-3s（超时即不可用）

任务 4: 端口预测序列预算
  - 基于 NAT 类型预生成端口预测序列
  - 缓存到本地，连接发起时直接取用
  - 耗时: < 10ms

任务 5: 本地保活间隔学习结果加载
  - 从本地缓存读取历史 Peer 的最优保活间隔
  - 耗时: < 1ms

预探测完成 → 标记 ready = true
```

### 3.9.2 连接发起的快速路径

```rust
fn initiate_connection(peer_id: &PeerId) {
    if self.preprobe_ready {
        // 快速路径：跳过探测，直接进信令交换 + 打洞
        // 节省 3-5s 探测时间
        start_signaling_and_punch(peer_id);
    } else {
        // 降级路径：预探测未完成，走完整流程
        wait_for_preprobe().await;
        start_signaling_and_punch(peer_id);
    }
}
```

### 3.9.3 缓存失效与刷新

| 缓存项 | 有效期 | 失效触发 |
|--------|--------|---------|
| net_time_anchor | 30 分钟 | 定时刷新 |
| NAT 类型 + 公网地址 | 5 分钟 | 定时刷新 + 网络切换（WiFi↔4G） |
| IPv6 入站状态 | 5 分钟 | 定时刷新 |
| 端口预测序列 | 5 分钟 | NAT 类型变化时失效 |
| Peer 保活间隔学习结果 | 永久（本地存储） | 断连恢复时重新学习 |

### 3.9.4 网络切换处理

```text
检测到网络切换（WiFi ↔ 4G/5G）:
  1. 立即标记 preprobe_ready = false
  2. 终止所有进行中的预探测任务
  3. 重新启动预探测（任务 1-4）
  4. 通知已连接 Peer：本地地址已变化，触发重新打洞
```

**关键特性**：所有预探测基于 Instant 定时（不读 SystemTime），网络切换时自动失效重探测，用户感知"打开客户端几秒后连接几乎瞬时"。

## 3.10 防火墙类型识别的探测包算法

### 3.10.1 防火墙类型分类

| 类型               | 描述                  | 对打洞的影响   |
| ---------------- | ------------------- | -------- |
| **无状态防火墙**       | 无连接追踪，仅按规则过滤（如 ACL） | 难，但可欺骗   |
| **有状态防火墙**       | 追踪连接状态，仅允许已建立连接的回包  | 较易，配合即可  |
| **应用层防火墙 (DPI)** | 深度包检测，识别协议          | 极难，需协议伪装 |

### 3.10.2 探测流程

```text
阶段 1: 单向探测 (入站权限)

  1. 信令服务器发送 UDP 包到 Client A 的 3 个端口:
     - 已知打洞端口 (高位端口)
     - 53 (DNS)
     - 443 (HTTPS)
  
  2. Client A 如果收到 → 该端口入站开放
  
  3. 延迟 500ms 再发一次 → 结合双向探测结果判断状态类型

阶段 2: 双向探测 (状态检测)

  4. Client A 先向服务器发送 UDP 包 (建立状态)
  5. 服务器立即用同一五元组回复 → Client A 收到
  6. 如果阶段 1 也收到 → 防火墙有状态检测 (会放行已建立连接)
  7. 如果阶段 1 未收到但阶段 2 收到 → 无状态防火墙/ACL (不追踪连接)
  8. 两个阶段都收不到 → 入站完全阻塞 (对称 NAT + 硬墙)

阶段 3: DPI 深度检测

  9. 发送多组不同协议的探测包:
     - 标准 UDP 格式
     - 伪装成 ICMP ping
     - 伪装成 DNS 查询 (53 端口)
     - 伪装成 QUIC Initial (443 端口)
  
  10. 根据哪组成功判断 DPI 过滤规则
```

### 3.10.3 边缘条件

| 场景             | 处理                      |
| -------------- | ----------------------- |
| 探测包被中间路由丢弃     | 多轮探测（每轮 3 次），2/3 成功即判定  |
| 防火墙动态规则        | 打洞期间持续重测，每 30 秒一次轻量探测   |
| DPI 对 DNS 伪装检测 | 使用真实 DNS 库构造合法 DNS 查询包体 |
| 探测端口被占用        | 尝试下一个端口（递增）             |

## 3.11 无状态防火墙的三次握手变种算法

### 3.11.1 原理

无状态防火墙仅检查 TCP 标志位：只允许设置了 SYN 的入站包（新建连接请求），或带有 ACK 的包（属于已建立连接）。通过模拟 TCP 三次握手的标志位顺序，欺骗防火墙放行 UDP 隧道的数据包。

### 3.11.2 算法实现

```text
本算法适用于 UDP 打洞通道被无状态防火墙阻断时的备用方案。

变种: TCP 封装打洞 (UDP in TCP)

步骤:
1. Client A → Client B [SYN]: 
   发送 TCP SYN 包 (到预测端口)
   源端口: 本地绑定端口
   序列号: 随机

2. Client B → Client A [SYN-ACK]: 
   收到 SYN 后回复 SYN-ACK (即使上层没有 TCP 监听)
   序列号: 随机
   确认号: SYN.Seq + 1

3. Client A → Client B [ACK]:
   回复 ACK
   确认号: SYN-ACK.Seq + 1
   
4. 连接建立! 此后无状态防火墙会放行该五元组的所有 TCP 包:
   后续传输业务数据时，将数据封装在 TCP 数据段中发送

变种: UDP 伪装 TCP (UDP with TCP header)
  
  适用: 防火墙仅检查包头部，不检查传输层协议
  方法: 在 UDP payload 前附加伪造的 TCP 头部，使防火墙误判为 TCP
  ⚠️ 欺骗成功率取决于防火墙的检查深度
```

### 3.11.3 与标准 TCP 打洞的区别

| 特征         | 标准 TCP 打洞     | 本变种            |
| ---------- | ------------- | -------------- |
| 连接状态       | 需要完整 TCP 栈    | 仅需要标志位序列伪装     |
| 可靠性        | 依赖 TCP 重传     | 上层自行处理可靠传输     |
| 适用防火墙      | 有状态（可协商）      | 无状态（欺骗 ACK 放行） |
| 在 NAT 上的存活 | TIME\_WAIT 限制 | 自定义心跳维持        |

### 3.11.4 边缘条件

| 场景                     | 处理                       |
| ---------------------- | ------------------------ |
| 防火墙深度检查到协议不匹配          | 降级到标准 TCP 封装隧道（性能下降但可连通） |
| 对端无原始套接字（Raw Socket）权限 | 使用用户态 TCP 栈（如 smoltcp）模拟 |
| 防火墙内核对伪造包丢包            | 仅作为最后手段，优先使用标准打洞         |
