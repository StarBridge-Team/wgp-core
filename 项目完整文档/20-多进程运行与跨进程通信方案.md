# WGP 多进程运行与跨进程通信方案

## 1. 目标与当前状态

当前 WGP 是进程内组合：`wgp-client` 持有客户端 DHT、房间运行时、打洞引擎和 `PortHub`；`wgp-node` 是独立 seed 进程；ET 适配器目前是同进程库加一个专用线程。DHT UDP 接收任务随节点生命周期退出，客户端/节点 Tokio worker 默认封顶为 4（`WGP_RUNTIME_WORKERS` 可覆盖）。本方案不是要求立刻拆分，而是规定后续 GUI、TUN、守护进程、ET 互通的进程边界和 IPC 契约。

目标：

- GUI 崩溃或升级不影响已建立的网络 agent；无需管理员权限的 UI 不持有 TUN 权限或长期私钥。
- 隧道密钥、打洞 UDP/TCP socket、保活与 `PunchedLink` 生命周期保持单一所有者。
- 控制和数据路径有界、可观测、能重连；IPC 不开放到公网，不引入新的业务中继。
- VPS seed、家宽贡献节点、桌面 client 可独立启停和升级。

非目标：把 P2P 数据流转成中心服务器转发；多个进程各持同一 DHT 身份私钥；第一阶段引入共享内存/零拷贝复杂度。

## 2. 推荐进程图

```text
Linux / Windows 用户会话
┌──────────────────────────────┐
│ wgp-ui                       │ 无特权；配置、成员和链路状态展示
└────────── IPC control ───────┘
                │ 本机受 ACL 保护的 stream IPC
┌───────────────▼──────────────┐
│ wgp-agent                    │ 每用户一个；持有 DHT identity、房间、
│                              │ Engine、PunchedLink、PortHub 与会话密钥
│ 进程内 Tokio + bounded tasks │ seed/bootstrap 仍走 UDP/TCP DHT
└───────────┬───────────┬──────┘
            │           │
   local framed IPC      │ 专用 WGP encrypted TunnelStream
            │           │
┌───────────▼───────┐   ▼
│ wgp-tun-helper    │  wgp-et-worker（可选独立进程）
│ 最小特权/管理员   │  只获得一个授权 ET stream；不接触 WGP 私钥
│ 只读写 TUN FD     │  不参与 seed 路由或 WGP Forward
└───────────────────┘

公网基础设施：wgp-node 独立 systemd 服务，与桌面 agent 生命周期分开。
```

### 进程职责

| 进程 | 生命周期 / 权限 | 持有的敏感状态 | 允许的接口 |
|---|---|---|---|
| `wgp-node` / `wgp-node-hobby` | systemd；专用低权限用户 | seed NodeIdentity、内存 KV/地址簿 | 公网 WGP UDP/TCP；不监听管理 IPC |
| `wgp-agent`（目标新增） | 每 OS 用户/服务实例；普通用户权限 | client NodeIdentity、会话密钥、Engine、已打通 socket | 本地 IPC；外连 seed/peer；显式暴露的本地转发端口 |
| `wgp-ui`（目标新增） | 用户登录会话；普通用户权限 | 无长期私钥；只缓存非敏感 UI 状态 | 仅连接本用户 agent 的 IPC endpoint |
| `wgp-tun-helper`（目标新增） | 按需短进程/受控服务；最小必要特权 | TUN handle；不持有 DHT identity | agent 发起的本地 IPC；不自行开公网监听 |
| `wgp-et-worker`（可选） | 由 agent 作为子进程启动 | ET network secret（只为所选 ET 网络） | 继承的专用隧道句柄或一次性 stream IPC |

第一阶段不要把 `Engine` 与 `PortHub` 拆成两个进程：UDP socket、keepalive 和 `PunchedLink` 当前以所有权转移方式交付，跨进程转移在 Linux `SCM_RIGHTS` 与 Windows socket duplication 之间存在平台差异。将它们留在 agent，可先获得 UI 崩溃隔离和普通用户/特权辅助隔离，而无需重写传输生命周期。

## 3. IPC 传输选型

### 本机控制面

- Unix/Linux：Unix domain stream socket，路径置于 `$XDG_RUNTIME_DIR/wgp/`（例如 `/run/user/<uid>/wgp/agent.sock`），目录 `0700`、socket `0600`；system service 使用 `/run/wgp/<instance>/`，属主为专用用户。
- Windows：Named Pipe（例如 `\\.\pipe\wgp-agent-<SID>`），DACL 仅允许当前用户 SID、SYSTEM 和必要管理员；禁止 `Everyone` 写入。
- 不将命名管道/UDS 映射为 TCP `0.0.0.0` listener。跨主机管理另做显式 SSH 隧道或 TLS/mTLS 服务，默认关闭。
- stream 使用长度前缀 framing；一次 frame 最大 1 MiB。握手先交换版本/feature，再验证 OS peer credentials；只有跨安全主体场景才加启动时一次性随机 token。不要只依赖随机 socket 路径作为认证。

### 数据面

- TUN helper 初期采用独立有界 stream IPC，单包消息按 IP packet 搬运；高吞吐量实测证明 IPC 拷贝成为瓶颈后，再评估平台共享内存环形队列。
- 数据包 IPC 采用 packet/datagram 语义：超 MTU 或超队列上限的包计数并丢弃；不可让 UDP/IP 数据在无界队列里积压。
- TCP 应用转发仍由 agent 内 `PortHub` 完成；不要把 TCP 字节逐帧请求/响应地穿过 UI 控制通道。
- `wgp-et-worker` 只接一条 agent 建立的 WGP 加密 stream。控制帧和数据帧是否拆为 stream/datagram 是后续性能任务；当前 PoC 的 ET 帧跑可靠流有队头阻塞，不应宣称已完成 TUN 数据面。

## 4. IPC 协议契约（IPC v1）

建议定义独立 `wgp-ipc` crate，协议消息用版本化、显式枚举的二进制 schema（首选 protobuf；若项目不愿新增运行依赖，可在构建期 codegen，运行时只保留 `prost`）。第一帧固定 header：

```text
magic(4) = "WGPI" | major(u16 LE) | minor(u16 LE) | flags(u16 LE) | body_len(u32 LE) | body
```

校验顺序：frame 长度不超过 1 MiB → magic/version → 消息类型及字段长度 → 请求主体授权 → 执行。未知 `major` 拒绝连接；未知可选字段/命令返回 `Unsupported`，不能静默把危险命令降级执行。

通用 envelope 至少包含：`request_id: u64`、`message_type`、`session_id`、可选 `deadline_ms`、payload。异步事件使用独立 `event_seq`；多进程重连后由 UI 发 `GetSnapshot`，按 snapshot 重建，不要求无限重放事件。

初始命令集：

- `GetVersion` / `GetCapabilities`
- `StartRoom` / `JoinRoom` / `LeaveRoom`
- `ListSessions` / `GetSnapshot`
- `SetPortForward` / `RemovePortForward`
- `WatchEvents` / `CancelRequest`
- `ShutdownAgent`（仅 agent 所有者或明确授权调用者）

不允许通用 `RunCommand`、任意文件路径读取、任意 shell、任意 socket bind。配置路径白名单化；seed/room code/secret 在日志里脱敏；身份私钥绝不通过 IPC 导出。

## 5. 并发、背压与故障语义

- 每条 IPC connection 的控制命令队列建议容量 128；单 session 上限由配置控制。满时返回 `Busy`，调用者退避重试，不能无限 `spawn`。
- 控制队列和数据队列分离；控制命令优先，但每轮最多处理 64 条后让出调度，确保 shutdown/health/watchdog 可运行。
- TCP stream 采用 bounded queue + backpressure；UDP/TUN datagram 使用 bounded queue，满时 drop-newest 或按 session policy drop-oldest，并暴露计数。禁止无界 `mpsc::unbounded_channel` 承载用户数据。
- 每个请求有 deadline；客户端断开时取消尚未执行的请求。状态改变类命令需幂等键，重复 `request_id` 不可重复创建 room/session。
- agent 崩溃后由 OS service manager 重启。UI 重新连接后查询 snapshot；正在进行的 NAT 协商失败由 agent 内既有重试逻辑恢复；DHT 节点身份和房间身份文件保持稳定路径。
- 有界队列溢出、frame 被拒、认证失败、版本不兼容都记结构化计数，默认日志不输出共享密钥、房间口令、完整 payload。

## 6. 密钥与权限

- client identity 文件 `0600`（Windows 当前用户专属 ACL）；seed identity 文件只给 `wgp` 服务账户读写，备份可恢复且不得多副本并行启动。
- `wgp-tun-helper` 不读取 `node_identity.key`、room secret 或 ET secret。agent 在启动 helper 时通过继承的匿名管道/一次性 capability 传达单次授权；token 用完即销毁。
- UDS 用 peer credentials 检查 UID/GID；Windows Named Pipe 检查 client token/SID。每个 IPC method 再做能力校验：普通 UI 不可控制别的用户 session，不可改 system seed 配置。
- 本机不加密传输由 OS 权限边界保护；IPC 跨越主机或容器网络 namespace 时必须启用双向 TLS 与短期证书，不能复用 WGP room secret。

## 7. 分阶段实施

1. **当前/阶段 0：单进程边界清理**。继续把 `wgp-client` 内部划分成 control/session/data 模块；给 channel、frame、队列加上限；明确 socket、密钥、身份文件唯一 owner。已经有的 DHT seed 仍由独立 `wgp-node` 进程运行。
2. **阶段 1：UI ↔ agent 控制 IPC**。新增 `wgp-agent` 承载现有 client runtime，CLI 与未来 GUI 均为 IPC client；先移植 `GetVersion`、`StartRoom`、`JoinRoom`、`GetSnapshot`、事件订阅。所有隧道和 socket 留在 agent。
3. **阶段 2：TUN helper**。只在确有 TUN 需求时新增特权 helper；先用有界 framed IPC，实测吞吐、CPU、丢包和延迟，再判断是否做共享内存。
4. **阶段 3：ET 子进程可选化**。把现有 `EtNode` thread 包装改为子进程 adapter；只向它暴露一条 WGP 隧道流和 ET 网络凭据，不共享 DHT 私钥。
5. 每阶段需有跨平台 IPC framing/权限/oversize/queue saturation/reconnect 测试；Linux 与 Windows 分别跑真实进程集成测试。未测 OS peer-credential 和 helper 重启行为前，不发布为稳定 API。

## 8. 当前实现限制

- 当前还没有 `wgp-agent`、IPC crate、TUN helper 或 ET 独立进程；以上为目标架构，不是已交付功能。
- `wgp-et-bridge` 的 `EtNode` 仍是同进程线程包装；握手在其线程同步运行且最长可阻塞约 30 秒。
- 所有跨进程行为方案需先解决 Windows Named Pipe 与 Linux UDS 的一致 framing、ACL 和生命周期测试，不能只根据回环单测判断完成。
