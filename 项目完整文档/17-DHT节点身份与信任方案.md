# 17 · DHT 节点身份与信任方案（"凭什么信你"）

> 立项背景：节点模式要从"客户端连种子"改为"每个节点向 DHT 宣告自己"（07 §5 第③层的落地）。
> 一旦人人可宣告，就必须回答一个协议问题：**收到一条宣告，凭什么相信它是正主，而不是冒充者？**
> 本文给出可实施的设计。核心结论：去中心化系统里"正主"无法被绝对证明，只能被**验证 + 背书 + 付费**，
> 因此方案是"三层可叠加的锚"+ "信任图"，且**根信任是配置项、不是代码常量**。

---

## 1. 三条必须分开的"信任"

把三件事混在一起谈，方案一定谈不清：

| 问题 | 含义 | 现有能力 |
|---|---|---|
| **A. 身份自证** | "这条宣告确实是我本人发的，没被改过" | ✅ 已有：ed25519 签名 + `node_id = SHA256(pubkey)` |
| **B. 名字归属** | "`seed.wgp.dev` 这个名字凭什么归这个公钥" | ❌ 缺 |
| **C. 可信度** | "这个节点值不值得被我当中继/观察者/存储" | ❌ 缺 |

A 已经有了（[advertise.rs](../kernel/wgp-dht/src/advertise.rs)、[id.rs](../kernel/wgp-dht/src/id.rs)），
B 和 C 才是"正主"问题的真正所在。**本方案只补 B 和 C，不动 A。**

## 2. 威胁模型

| 攻击 | 说明 | 对应防线 |
|---|---|---|
| **冒充既有节点** | 伪造 `node_id` 抢占别人在路由表里的位置 | A 已解决：没有私钥签不出宣告 |
| **冒名顶替（新身份）** | 自己生成密钥对，把节点叫 `seed.wgp.dev` | B：名字要能被独立验证 |
| **女巫攻击（sybil）** | 批量生成 N 个身份，占满路由表/投票 | L3 准入成本 + 路由表卫生 |
| **日蚀攻击（eclipse）** | 把受害者的桶全填成自己的节点，切断它与真实网络的联系 | 每 /24 限入 + 随机化刷新 |
| **地址投毒** | 宣告一个假地址，把流量引到自己这儿（中间人或黑洞） | 宣告签名绑定地址 + 探活校验 |
| **重放** | 拿旧宣告反复注册 | 报文带 epoch/时间窗，接收端单调递增校验 |

## 3. 设计原则

1. **身份自持**：节点自己生成密钥，没有任何"发证机构"审批。谁都能加入——但能不能被**信**是另一回事。
2. **根信任可替换**：客户端内置的是**若干公钥指纹 / 域名**（`trust_roots`），不是 IP、不是写死的官方地址。
   别人 fork 我们的代码，换成自己的根，就是一个独立运行的网络——**这正是"我们不维护了、别人还能用"的技术前提**。
3. **协议里不出现"官方"二字**：官方节点只是默认 `trust_roots` 里的几项配置，和第三方节点走完全相同的验证路径。
4. **信任可衰减、可撤销**：所有背书带有效期，不续签自然失效（等价于"持续维护"）。

## 4. 方案：四层

### L0 · 身份自证（已有，不改）

- 长期密钥：ed25519，持久化在 `node_identity.key`（32B 种子）。
- `node_id = SHA256(pubkey)`，天然自证绑定。
- 宣告与 RPC 响应均带签名；PING/PONG 交换公钥并校验 `SHA256(pk) == node_id`。

### L1 · 名字锚定（"正主"）——三把锚，可叠加

节点要在宣告里说明"我叫什么、这个名字凭什么归我"。三种锚定方式，**按可信度递减、按部署成本递增**：

#### 锚 ①：域名锚（DNS TXT）——最强，且不需要我们维护

```
_wgp.seed.example.com.  IN TXT  "wgp1=<base32(ed25519_pubkey)>"
```

- **正主 = 控制该域名的人**。域名所有权是全世界通行的既成信任，不需要我们做 CA，也不需要我们维护。
- 任何客户端都能独立验证：查 TXT → 比对公钥 → 比对 node_id。
- 换 IP 不影响信任（信任绑公钥，不绑地址）。
- 缺点：需要用户有个域名（几块钱/年）。

#### 锚 ②：背书锚（已有节点签名）——零门槛，靠社交图

```
Endorsement {
    subject_pubkey : [u8;32]   // 被背书的节点
    endorser_pubkey: [u8;32]   // 背书人（自己已有可信度）
    scope          : u8        // 允许的角色位：relay/observer/store/bootstrap
    issued_at      : u64       // 毫秒
    expires_at     : u64       // 建议 30 天，需续签
    sig            : [u8;64]   // endorser 签名
}
```
共 32+32+1+8+8+64 = **145B**，存 DHT KV：`key = SHA256("wgp/endorse/v1" ‖ subject_pubkey)`，值为背书记录列表。

- 官方初始的 3 个节点互为背书，构成"根"；新节点找它们要背书即可入网。
- **背书是有限的**：每节点每 24h 最多签 N 张（本地限制），且背书人自己掉信任会连带影响下游。

#### 锚 ③：TOFU（首次使用信任）——兜底，不推荐单独使用

第一次见到这个 node_id 就记住（本地 `known_nodes.json`）；之后再看到同名的不同公钥 → **告警 + 拒绝自动覆盖**。
适合"我自己的两台机器互连"这种场景，不适合公共节点。

> 三把锚的组合：**① 优先、② 兜底、③ 兜自己的私活**。三者都由同一套 `TrustStore` 统一评分。

### L2 · 信任图与权重

```
trust_score(node) = Σ over endorsers e  w(e) × decay(hops(e → root))

w(root)      = 1.00        （trust_roots 里列出的指纹/域名）
w(depth 1)   = 0.50        （根直接背书的）
w(depth 2)   = 0.25
w(depth ≥3)  = 0.125       （封顶，不再衰减，避免长链洗白）
```

- `trust_score ≥ 1.0` → 可当 `bootstrap`（给别人当种子）
- `≥ 0.5` → 可当 `relay` / `observer` / `store`
- `< 0.5` → 只能当普通成员（能加入、能被连，但不被依赖）

这条规则的含义：**"可信"不是自称的，是别人给的，并且要够多人才算数。**

### L3 · 准入成本与路由表卫生

| 措施 | 目的 | 代价 |
|---|---|---|
| **轻量 PoW**：`node_id` 前 16–20 bit 为 0 才允许入路由表 | 让"造 10 万个身份"从秒级变成小时级 | 每节点启动时算 1 次，几秒 |
| **每 /24 限入 K 个**（K=2~4） | 抗日蚀 | 无 |
| **入表需双向 PING 成功 + 签名校验** | 抗地址投毒 | 无 |
| **桶随机化刷新**（每 10 分钟挑一个桶重新 FIND_NODE） | 抗日蚀 | 少量流量，受预算闸门约束（H6） |

## 5. 线格式改动（具体到字节）

现有 `SeedAdvertise` 定长 91B：

```
[0..2]  magic        [2] type=0x20
[3..7]  addr_v4      [7..9] dht_port   [9..11] stun_port
[11]    priority     [12] flags
[13..27] 14B 保留（当前全 0）   ← 正好放新字段
[27..91] ed25519 签名(64B)
```

**改动（向后兼容）**：把 14B 保留位定义为

```
[13..21] epoch_ms 低 64 位   （抗重放；接收端要求单调递增）
[21..23] endorse_count       （背书数，仅作提示，不作信任依据）
[23..27] name_hash_prefix    （SHA256(名字) 前 4B，供快速匹配）
```

- 老节点读到非零保留位 → 按现有语义忽略（签名覆盖到 [0..27]，所以改动会自然让老节点验签失败……
  **因此需同时把 `PROTO_VERSION` +1，按版本分支解析**，或另开 `type=0x21` 的新报文。
  **推荐后者**：`SeedAdvertiseV2 (type=0x21, 115B)`，带 `subject_pubkey(32)`，彻底摆脱"要额外信道取公钥"的约束。
- 背书记录**不进**广告报文（太长），走 DHT KV。

[[root]]

## 7. 分阶段实施

| 阶段 | 内容 | 工作量 | 上线后能看到什么 |
|---|---|---|---|
| **P0** | 广播 + 接收 `AdvertiseV2`；`TrustStore` 只做 TOFU + 静态 `trust_roots` | **2–3 天** | 节点自动互相发现，不再依赖手工种子清单 |
| **P1** | 背书 RPC + KV 存储 + 评分；`endorse` 子命令 | **3–5 天** | 官方节点能给新节点背书；可信节点自动获得 relay 权限 |
| **P2** | 域名锚（DNS TXT 校验）+ PoW + 路由表 /24 与分桶 | **5–7 天** | 抗 sybil/日蚀；运营者可用自己的域名声明正主 |

P0 做完就已经解决"节点模式改成 DHT 节点"：**宣告接线 + 互相发现**。P1/P2 是把"可信"补齐。

## 8. 待拍板的问题

1. **P0 阶段先不校验信任**：任何人都能宣告，先跑通发现链路。可接受吗？（我认为可以——早期用户少，滥用动力低。）
2. **官方根用哪种锚**：域名锚（需要买个域名，但最正规）还是纯背书锚（零成本，但"官方"只是"三个互相背书的节点"）？
3. **PoW 位数**：16 bit ≈ 手机 1 秒、服务器 0.05 秒；20 bit ≈ 手机 16 秒。取 18 bit 折中？
4. **背书有效期**：30 天续签，对家用宽带的贡献节点是否太频繁？

## 9. 与 EasyTier 的关系

本方案与 ET 兼容**互不依赖**：ET 桥接解决"和外部网络互通"，本方案解决"自己网络内部怎么互信地发现"。
若将来要互通 ET 公共节点，只需在 `TrustStore` 里加一个锚类型（`easytier-public-node`），评分逻辑不变。

## 10. P0 实现记录（2026-11-15）

§7 的 P0 已落地，范围是「广播 + 接收广告、节点互相发现」。**没有做** `TrustStore`、TOFU 与静态 `trust_roots`——
P0 完全不校验信任（§8 第 1 条的约定）。代码以 `kernel/wgp-dht/src/{advertise,directory,node}.rs` 为准，与上文草案的出入如下。

### 10.1 广告 V2 定版布局（type=0x21，123B）

```
[0..2]    magic "WG"        [2]      type = 0x21
[3..7]    addr_v4           [7..9]   dht_port（非 0）
[9..11]   stun_port（0 = 不提供观察者）
[11..13]  tcp_port （0 = 不提供 TCP 信令）
[13]      priority          [14]     flags（bit0 = 允许 Forward 中转）
[15..23]  epoch（u64 BE）
[23..27]  name_hash（未命名全 0；P0 不解释）
[27..59]  pubkey（ed25519；node_id = SHA256(pubkey)）
[59..123] signature = ed25519("wgp/seed-adv/v2" ‖ [0..59])
```

与 §5 草案的差别：

- 草案写 115B，算术有误：既有 91B 布局加 32B 公钥是 123B。
- 用 `tcp_port`（2B）取代了草案里的 `endorse_count`（2B）：背书数只是提示、不作信任依据，P1 可以直接数背书记录；
  TCP 信令端口则是客户端现在就需要的。
- 签名覆盖签名之前的全部字节（含魔数与类型），并加域分隔前缀：同一把身份密钥还要签房间记录与报道请求。
- `priority` 只透传、不参与任何选择——自称的优先级不可信，等 P1 的评分接手。

### 10.2 纪元（epoch）不是时间

§5 写的是 `epoch_ms`。但项目禁读系统时钟（H5），所以纪元改为**启动计数**：`wgp-node` 把它存在身份文件旁的
`node_identity.epoch`，每次启动 +1，纪元 = 计数 << 32。接收端只采纳比已有的更大的纪元。
文件丢失的后果只是：已经认识该节点的人继续沿用旧广告，直到旧端点探活失败被逐出后才重新采纳。

### 10.3 入表规则

一条广告要进种子目录：验签通过 → 纪元比已有的大 → **在所报地址上 PING，且应答者的身份就是广告主**。
同一地址上的更新广告直接生效，换地址必须重新探活。目录上限 64 条；满员时只有用户自己配置的入口种子能挤位；
一个端点只认一个身份；每 20s 探活一次，连续 3 次不应答即逐出。§4 L3 里的 PoW 与 /24 限入没有做。

### 10.4 传播

- 推送：宣告中的节点每 60s 把自己的广告发给已知种子与配置的入口端点（定长报文，无应答）。
- 索取：RPC `FIND_SEEDS(target)` / `SEEDS`，返回对方已知的、离 target 最近的至多 8 条广告原文。
  请求必须填充到不短于期望的应答——应答永远不长于请求，不给 UDP 反射放大留口子。
- 扩散：迭代 FIND_NODE 把沿途可达的节点认识一遍，再向它们索取广告。

命令行：`wgp-node --advertise <公网IPv4> [--peers udp://其他种子:11010,...]`。客户端不宣告，只索取与扩散。

### 10.5 P0 没有解决的

- 任何人都能宣告，并可能被客户端选为房间记录的存储节点与信令中转者；目录里的种子只代表「存在且连得上」。
- PING / PONG 不带签名，探活证明的只是「该地址上有人自称是这个身份」。
- 「谁来宣告」仍是待决项：现在只有配了 `--advertise` 的节点宣告。§8 的四条也都还没有结论。

## 11. 线协议变更：探活身份证明（一次性挑战响应）

> 状态：**2026-11-16 定稿并已实现**（审阅稿 → 代码：`wgp-proto::dht` 的三个 `AUTH_*` 体、`wgp-dht::auth`、
> `DhtNode` 的挑战响应状态机）。本节取代 §10.5 第 2 条「PING/PONG 不证明私钥持有权」。
> 影响面：`kernel/wgp-proto/src/dht.rs`、`kernel/wgp-proto/src/consts.rs`、`kernel/wgp-dht/src/{node,auth}.rs`。
> 不改名、不改动既有的 0x30～0x3A 报文体；新增三个类型号，老节点按「未知类型」丢弃（见 §11.6）。

### 11.1 问题：为什么不能只给 PING 加签名

现网语义里，「探活」同时承担两件事：证明**这个地址上有人**，以及**这个人就是它自称的 NodeId**。
第 3.2 节记录的攻击是：攻击者录下某已知节点的一条报文，在**另一个地址**上重放，接收方就把该节点的地址簿条目改到攻击者那里——
之后所有 Forward 中转、房间报道都投给攻击者。如果只是把 PING 变成「带签名的 PING」，攻击者仍然可以重放**旧签名**：
签名绑定的是内容而不是「这一次询问」，录下来的报文永远有效。所以必须让对端证明**它现在能对本次专用的随机数签名**。

也不采用「PING 里加时间戳」：项目禁读系统时钟（H5），跨进程时间不可比，时间窗只能靠接收端本地时钟判断，
且无法区分「录了 20 秒前那条」和「刚刚那条」。

### 11.2 设计要点

| 要求 | 落法 |
|---|---|
| 证明私钥持有权 | 对端用长期 ed25519 身份密钥签名 |
| 抗重放 | 签名覆盖**验证方刚刚生成的一次性 nonce**（16B），且每个挑战只用一次 |
| 抗跨用途挪用 | 域分隔前缀 `wgp/dht-auth/v1`（与 `wgp/seed-adv/v2`、房间记录、报道请求前缀互不可挪用） |
| 绑定双方身份 | 签名覆盖 prover_id 与 verifier_id；两者都要过 `node_id == SHA256(pubkey)` |
| 绑定这次往返 | 签名覆盖 RPC 头部 txid |
| 双向（种子/存储节点要认识客户端） | 证明报文里带证明方自选的 `prover_nonce`，验证方用它回证，1.5 RTT 双向完成 |
| 验证前不改状态 | 路由表 / 地址簿只在「签名 + nonce + 来源地址 + 未过期」全部通过之后写入 |
| 结果可诊断 | 版本/格式不合法时回 `AUTH_REJECT`（带原因），不是静默超时 |

握手由**发起方**启动：谁想认识谁，谁发挑战。这与现有「PING 双向学习」的用法一致（客户端 ping 种子、锚点 ping 存储节点），
所以调用点几乎不变，`DhtNode::ping()` 内部换成握手即可。

### 11.3 线格式（定长，手写编解码）

三个新类型号，落在既有 RPC 头（`magic "WG" | type | txid(4B BE)`）之后：

```
AUTH_CHALLENGE = 0x3B   体 81B
[0..32]   verifier_id        挑战方 NodeId
[32..64]  verifier_pubkey    挑战方长期公钥（接收方校验 SHA256(pubkey)==verifier_id）
[64..80]  nonce              一次性挑战，16B，密码学随机
[80]      version            = 1

AUTH_PROOF     = 0x3C   体 161B
[0..32]   prover_id          证明方 NodeId
[32..64]  prover_pubkey      证明方长期公钥
[64..80]  nonce_echo         原样回抄收到的挑战 nonce
[80..96]  prover_nonce       证明方自选的一次性 nonce（不要求回证时全 0）
[96]      version            = 1
[97..161] signature          64B

AUTH_REJECT    = 0x3D   体 2B
[0]       reason             1=版本不支持  2=请求非法  3=限速
[1]       supported_version  reason=1 时填本端支持的版本，否则 0
```

**待签名消息（117B，两个方向同一套）**：

```
"wgp/dht-auth/v1"(16B) ‖ version(1) ‖ prover_id(32) ‖ verifier_id(32)
                       ‖ nonce_echo(16) ‖ prover_nonce(16) ‖ txid(4, BE)
```

- 字段顺序固定、长度定长：不存在「两边各自拼装字段」的歧义，签名方与验签方都从报文与头部字节取。
- `version` 在签名覆盖范围内：将来出现 v2 时，v1 的证明不会被当成 v2 的证明（也防止中间人把版本降级后复用签名）。
- txid 在头部、不在体里，但它被签名覆盖，所以「把证明挪到另一个 txid 的事务里」会验签失败。

### 11.4 握手时序

```
A（发起方）                                              B（应答方）
  |  AUTH_CHALLENGE txid=t1, nonce_a  -------------------->|
  |                                                        |  1. 校验 verifier_id 绑定
  |                                                        |  2. 记下 nonce_b（自选），发证明
  |<--  AUTH_PROOF   txid=t1, nonce_echo=nonce_a,          |
  |     prover_nonce=nonce_b, sig_b                        |
  |  3. 验签 → 学 B@源地址                                  |
  |  AUTH_PROOF txid=t2, nonce_echo=nonce_b,               |
  |     prover_nonce=0, sig_a  --------------------------->|
  |                                                        |  4. 验签 → 学 A@源地址
```

- 第 1 步**不产生任何学习**：A 只是花了一个 16B nonce；B 也不因收到挑战而学习 A（否则伪造挑战即可毒化 B）。
- 第 2 步 B 证明；A 验签通过才写 A 的路由表/地址簿。
- 第 3 步 A 回证（fire-and-forget，丢了就等下一轮维护），B 验签通过才写 B 的表。**种子的地址簿就是这样学到 NAT 后的客户端的**——
  仍然不需要客户端事先宣告，也不需要客户端有固定端口。
- 双向都是「先验后写」。任一方向失败，另一方向的状态不受影响（不会因为对方不回应就污染自己的表）。

### 11.5 状态、上限与限速

| 状态 | 位置 | 上限 | 过期 |
|---|---|---|---|
| 待应答的挑战 | A：`pending`（txid → 目标地址 + nonce + oneshot） | 64 条（满则拒绝新 ping，返回 `Busy`） | 1.5s（与 RPC 超时一致） |
| 已发出的回证挑战 | B：`issued`（nonce → 来源地址 + 时刻） | 512 条，插入时先清扫 | 30s |
| 单次证明 | 无（一次性，验完即删） | — | — |

- **入站挑战应答限速**：全局每秒 128 条（固定窗口）、单源 IP 每秒 16 条（表上限 1024，插入时清扫过期）。超限**静默丢弃**——
  回一个 `AUTH_REJECT` 只会替攻击者放大流量。想区分「被限速」与「对端不在」的一方，靠本地计数与重试退避判断。
- **放大倍数**：请求 88B（头 7 + 体 81）、应答 168B（头 7 + 体 161），约 1.9 倍；单 IP 限速把它压到 ~3KB/s，
  且 `AUTH_PROOF` 不能触发对第三方的流量（回证发往「发挑战的那个地址」，而那个地址本来就是发起方）。
- 既有 `PING` 仍 1:1（71B↔71B），`FIND_SEEDS` 保持「应答不长于请求」。

### 11.6 升级与兼容策略

**版本轴 = 类型号。** `0x3B/0x3C/0x3D` 就是「身份证明 v1」；体里的 `version` 字节留给同一组类型号内的小改动。
这与 §10.1 用 `0x21` 而不是改 `0x20` 的做法一致：老节点遇到不认识的类型号，`RpcHeader::decode` 直接返回 `None` 并静默丢弃，
不会误解析，也不会崩。

| 组合 | 行为 |
|---|---|
| 新 ↔ 新 | 走挑战响应；`AUTH_*` 是唯一能写路由表/地址簿的路径 |
| 新 → 老（严格模式，默认） | 老节点丢弃 `AUTH_CHALLENGE` → 新节点在 1.5s 后得到 `RpcError::Unverified`，错误信息明确写「对端不支持身份证明」；**不学习** |
| 新 → 老（`--allow-legacy-identity`） | 握手超时后回退到旧 `PING/PONG`，用 PONG 学习（与旧行为等价）；日志与计数器标记为 `legacy` |
| 老 → 新 | 老节点发 `PING`，新节点仍回 `PONG`（只为存活/兼容，不产生学习）；老节点发 `STORE`/`FORWARD` 照旧处理，但新节点不因此写地址簿 |
| 版本不支持 | 新节点收到 `version≠1` 的挑战 → `AUTH_REJECT(1, supported=1)`；发起方据此立即失败并给出可读原因 |

- **广告能力位**：`SeedAdvertiseV2.flags` 增加 `FLAG_AUTH_V1 = 0x02`（bit0 仍是 relay）。老节点验签时把 flags 当不透明字节，
  不受影响；新节点据此在**入表之前**就知道这个种子支不支持身份证明，能提前给出「需要升级对端」的提示，而不是等到探活超时。
- **不设静默降级**：严格模式下绝不「验证失败就退回 PONG 学习」。要兼容旧节点必须显式开开关——把安全降级变成运营者的决定。
- **回滚**：删掉 `FLAG_AUTH_V1` 位并启用 `--allow-legacy-identity` 即回到旧行为；报文格式不变，不需要回滚线格式。
- **协议版本常量**：`PROTO_VERSION` 仍为 `0x01`。DHT RPC 头本来就不携带它（见 `RpcHeader` 布局），
  真正的协商手段是「类型号 + 体里的 version + ADVERT flags」，因此这次不动它，避免让一个不参与解析的常量制造版本幻觉。

### 11.8 仍然不解决的问题（写进 §2.5 式的账）

1. **在线中继（relay）**：攻击者若能在同一时刻既收下我们的挑战，又能把 `AUTH_PROOF` 转发给受害者，就能让我们把「受害者的身份」
   学到攻击者的地址上。这是挑战响应固有的边界——只要通道本身没有地址认证，任何「证明我是谁」都不能证明「我在这个地址上」。
   后果是**地址被投毒（可用性）**而不是**身份被冒充（机密性）**：之后发往该地址的报文到不了正主，探活连续失败 3 次即淘汰该条目。
   要彻底解决需要 STUN 回显地址参与签名（依赖观察者，见 07 §3）或路径认证，属于后续工作。
2. **女巫 / 日蚀**：新身份可以无限生成。这次不引入 PoW 与 /24 限入（§4 L3，P2）。
3. **CPU 消耗**：攻击者仍可让我们做 ed25519 验签，靠 §11.5 的限速与「验签前先做便宜的格式/绑定校验」把成本压住。
4. **不改变信任语义**：证明「它持有这把私钥」不等于「它可信」。§4 的 L1/L2 评分照旧待做。

与草案的出入（以代码为准）：

1. **限速超限静默丢弃**，不回 `AUTH_REJECT(3)`（见 §11.5）。
2. **`AUTH_REJECT` 只用于版本不支持与显式拒绝**：格式非法 / 绑定失败一律静默丢弃——回包等于替攻击者放大。
3. **TCP 一侧完全不写路由表与地址簿**。草案只说「不写地址簿」；实现进一步不写路由表——只入路由表而没有地址的条目
   永远不会被 `probe_routing_batch` 探到，也就永远不会被淘汰，是纯粹的死条目。
4. **`STORE` 不再学习写入者**。存储节点靠客户端 upkeep 里的 `ping()`（现在是一次完整握手）认识它，
   所以「加入→报道→中转」的时序不变，只是第一次报道可能早于互认——报道本身是 fire-and-forget 且客户端会重试，不受影响。
5. **回证 nonce 只有「地址 + 期限」都对得上才被消费**：知道 nonce 的人无法抢先烧掉合法回证。
6. **严格模式的失败诊断**：握手超时后追加一次旧 `PING`（800ms，不学习）。收到 `PONG` → 返回 `RpcError::Unverified`
   （`explain()` 文案「对端不支持身份证明」）；收不到 → `RpcError::Timeout`。`legacy_fallback_count()` 可观测。

重放、回证重放、版本拒绝、洪流限速、严格模式不学习、兼容模式学习、换端点恢复、闸门窗口）；`net_test` 的既有学习断言
改为等待回证落地（回证是 fire-and-forget）。
